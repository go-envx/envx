`envx.yaml` is the workspace manifest: it declares your environments, your projects, and the settings that shape how envx resolves them. This page is the structural reference for every key. To see a manifest built from scratch, follow [Getting Started](../../guide/getting-started/). To learn how envx locates the manifest, see [Discovery](../discovery/).

:::

## Manifest

  The top-level object of `envx.yaml`.

### `environments`

  <SchemaMeta type="string[]" required />

  The ordered list of environments you can resolve against. The first entry is the default when [`env`](#env) is not specified.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - staging
        - production
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `settings`

  <SchemaMeta type="Settings" />

  Global [Settings](#settings-2) applied to every project.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      settings:
        prefix: APP
        delimiter: ","
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `projects`

  <SchemaMeta type="map[string]Project" required />

  A map of project name to its [`Project`](#project) definition. Declare at least one.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      projects:
        api-service:
          includes:
            - env/database
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Project

  One entry under [`projects`](#projects).

### `includes`

  <SchemaMeta type="string[]" required />

  The ordered list of namespaces to merge. Each entry `<dir>/<name>` resolves to a base `<dir>/<name>.yaml` and an overlay `<dir>/<name>.<environment>.yaml`. Namespaces merge in declaration order, so when two define the same key, the one listed last wins.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      projects:
        web:
          includes:
            - database
            - overrides
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # database.yaml
      host: db.local
      port: 5432
      ```

      ```yaml
      # overrides.yaml
      host: override.local
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      # overrides is listed last,
      # so it wins over database.

      envx get web HOST
      # override.local

      envx get web PORT
      # 5432
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `settings`

  <SchemaMeta type="Settings" />

  Project-level [Settings](#settings-2) that override the global ones.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        prefix: APP

      projects:
        api:
          settings:
            suffix: V2
          includes:
            - values
        web:
          settings:
            prefix: WEB
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web WEB_HOST
      # localhost

      envx get api APP_HOST_V2
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Settings

  Every setting can be declared globally (the top-level [`settings`](#settings) block) or per project (a project's [`settings`](#settings-1) block), and each can also be supplied as a CLI flag or an `ENVX_*` environment variable. When the same setting is set in more than one place, [Settings Resolution](../settings-resolution/) decides which one wins. Each example below pairs a minimal workspace with a command that resolves the setting.

### `delimiter`

  <SchemaMeta type="string" />

  The string used to join a list-valued leaf into a single variable, so `[db-a.local, db-b.local]` becomes `db-a.local,db-b.local`.

  - **CLI Flag:** `--delimiter`
  - **Environment Variable:** `ENVX_DELIMITER`
  - **Default Value:** `","`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        delimiter: ";"

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      hosts:
        - db-a.local
        - db-b.local
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOSTS
      # db-a.local;db-b.local

      ENVX_DELIMITER=" " envx get web HOSTS
      # db-a.local db-b.local

      envx get web HOSTS --delimiter "|"
      # db-a.local|db-b.local
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `env`

  <SchemaMeta type="string" />

  The environment to resolve. It selects which `<namespace>.<environment>.yaml` overlays are layered on top of each base file. It must be one of the environments declared in [`environments`](#environments).

  - **CLI Flag:** `--env`, `-E`
  - **Environment Variable:** `ENVX_ENV`
  - **Default Value:** first declared environment in `environments`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - production

      settings:
        env: production

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: # set per environment
      ```

      ```yaml
      # values.development.yaml
      host: dev.local
      ```

      ```yaml
      # values.production.yaml
      host: prod.internal
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST
      # prod.internal

      ENVX_ENV=development envx get web HOST
      # dev.local

      envx get web HOST -E development
      # dev.local
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `namespace_prefix`

  <SchemaMeta type="bool" />

  Prefix each key with the name of the namespace it came from. Most workspaces avoid this by nesting shared namespaces, but it is useful when flat namespaces collide. In the example below, the `worker` project includes `cache` and `queue`, which both define `host` and `port`.

  - **CLI Flag:** `--namespace-prefix`
  - **Environment Variable:** `ENVX_NAMESPACE_PREFIX`
  - **Default Value:** `false`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      projects:
        worker:
          settings:
            namespace_prefix: true
          includes:
            - cache
            - queue
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # cache.yaml
      host: cache.local
      port: 6379
      ```

      ```yaml
      # queue.yaml
      host: queue.local
      port: 5672
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get worker CACHE_HOST
      # cache.local
      envx get worker QUEUE_HOST
      # queue.local

      # Turn it off and the flat keys collide — the last include wins.
      ENVX_NAMESPACE_PREFIX=false envx get worker HOST
      # queue.local

      envx get worker HOST --namespace-prefix=false
      # queue.local
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `overload`

  <SchemaMeta type="bool" />

  Let values from your files override existing OS environment variables. Applies to [`run`](../../commands/run/); by default an existing OS variable wins.

  - **CLI Flag:** `--overload`
  - **Environment Variable:** `ENVX_OVERLOAD`
  - **Default Value:** `false`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        overload: true

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      name: from-file
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      NAME=from-os envx run web -- printenv NAME
      # from-file

      ENVX_OVERLOAD=false NAME=from-os envx run web -- printenv NAME
      # from-os

      NAME=from-os envx run web --overload=false -- printenv NAME
      # from-os
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `prefix`

  <SchemaMeta type="string" />

  Prepended to every resolved key, uppercased and joined with an underscore, so `app` turns `HOST` into `APP_HOST`.

  - **CLI Flag:** `--prefix`
  - **Environment Variable:** `ENVX_PREFIX`
  - **Default Value:** `""`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        prefix: app

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      port: 8080
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web APP_HOST
      # localhost

      ENVX_PREFIX=svc envx get web SVC_HOST
      # localhost

      envx get web SVC_HOST --prefix svc
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `require_overlays`

  <SchemaMeta type="bool" />

  Require every overlay file in a project's namespace chain to exist. A missing overlay becomes an error instead of being silently skipped.

  - **CLI Flag:** `--require-overlays`
  - **Environment Variable:** `ENVX_REQUIRE_OVERLAYS`
  - **Default Value:** `false`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - staging

      settings:
        require_overlays: true

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST --env staging
      # Error: loading environment file values.staging.yaml: open values.staging.yaml: no such file or directory

      ENVX_REQUIRE_OVERLAYS=false envx get web HOST --env staging
      # localhost

      envx get web HOST --env staging --require-overlays=false
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `suffix`

  <SchemaMeta type="string" />

  Appended to every resolved key, uppercased and joined with an underscore, so `v2` turns `DATABASE_HOST` into `DATABASE_HOST_V2`.

  - **CLI Flag:** `--suffix`
  - **Environment Variable:** `ENVX_SUFFIX`
  - **Default Value:** `""`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        suffix: v2

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST_V2
      # localhost

      ENVX_SUFFIX=beta envx get web HOST_BETA
      # localhost

      envx get web HOST_BETA --suffix beta
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>
