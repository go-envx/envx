`envx.yaml` is the workspace manifest: it declares your environments, your projects, the settings that shape how envx resolves them, and optionally your [secrets](#secrets) store and [validation](#validate) severities. This page is the structural reference for every key. To see a manifest built from scratch, follow [Getting Started](../../guide/getting-started/). To learn how envx locates the manifest, see [Discovery](../discovery/).

The manifest is decoded strictly: an unknown key is rejected with a "Did you mean" suggestion for the closest valid key and a link back to this page.

## Manifest

  The top-level object of `envx.yaml`.

### `environments`

  <SchemaMeta type="string[]" required />

  The ordered list of environments you can resolve against. The first entry is the default when [`env`](#env) is not specified.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - staging
        - production
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `settings`

  <SchemaMeta type="Settings" />

  Global [Settings](#settings-2) applied to every project.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      settings:
        prefix: APP
        delimiter: ","
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `projects`

  <SchemaMeta type="map[string]Project" required />

  A map of project name to its [`Project`](#project) definition. Declare at least one.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      projects:
        api-service:
          includes:
            - env/database
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Project

  One entry under [`projects`](#projects).

### `includes`

  <SchemaMeta type="string[]" required />

  The ordered list of namespaces to merge. Each entry `<dir>/<name>` resolves to a base `<dir>/<name>.yaml` and an overlay `<dir>/<name>.<environment>.yaml`. Namespaces merge in declaration order, so when two define the same key, the one listed last wins.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      projects:
        web:
          includes:
            - database
            - overrides
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # database.yaml
      host: db.local
      port: 5432
      ```

      ```yaml
      # overrides.yaml
      host: override.local
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      # overrides is listed last,
      # so it wins over database.

      envx get web HOST
      # override.local

      envx get web PORT
      # 5432
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `settings`

  <SchemaMeta type="Settings" />

  Project-level [Settings](#settings-2) that override the global ones.

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        prefix: APP

      projects:
        api:
          settings:
            suffix: V2
          includes:
            - values
        web:
          settings:
            prefix: WEB
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web WEB_HOST
      # localhost

      envx get api APP_HOST_V2
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Settings

  Every setting can be declared globally (the top-level [`settings`](#settings) block) or per project (a project's [`settings`](#settings-1) block), and each can also be supplied as a CLI flag or an `ENVX_*` environment variable. When the same setting is set in more than one place, [Settings Resolution](../settings-resolution/) decides which one wins. Each example below pairs a minimal workspace with a command that resolves the setting.

### `delimiter`

  <SchemaMeta type="string" />

  The string used to join a list-valued leaf into a single variable, so `[db-a.local, db-b.local]` becomes `db-a.local,db-b.local`.

  - **CLI Flag:** `--delimiter`
  - **Environment Variable:** `ENVX_DELIMITER`
  - **Default Value:** `","`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        delimiter: ";"

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      hosts:
        - db-a.local
        - db-b.local
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOSTS
      # db-a.local;db-b.local

      ENVX_DELIMITER=" " envx get web HOSTS
      # db-a.local db-b.local

      envx get web HOSTS --delimiter "|"
      # db-a.local|db-b.local
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `env`

  <SchemaMeta type="string" />

  The environment to resolve. It selects which `<namespace>.<environment>.yaml` overlays are layered on top of each base file. It must be one of the environments declared in [`environments`](#environments).

  - **CLI Flag:** `--env`, `-E`
  - **Environment Variable:** `ENVX_ENV`
  - **Default Value:** first declared environment in `environments`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - production

      settings:
        env: production

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: # set per environment
      ```

      ```yaml
      # values.development.yaml
      host: dev.local
      ```

      ```yaml
      # values.production.yaml
      host: prod.internal
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST
      # prod.internal

      ENVX_ENV=development envx get web HOST
      # dev.local

      envx get web HOST -E development
      # dev.local
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `overload`

  <SchemaMeta type="bool" />

  Let values from your files override existing OS environment variables. Applies to [`run`](../../commands/run/), where by default an existing OS variable wins. It also decides whether file values or host variables win in [`{{VAR}}` substitution](../../concepts/variable-substitution/) for every command that resolves values.

  - **CLI Flag:** `--overload`
  - **Environment Variable:** `ENVX_OVERLOAD`
  - **Default Value:** `false`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        overload: true

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      name: from-file
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      NAME=from-os envx run web -- printenv NAME
      # from-file

      ENVX_OVERLOAD=false NAME=from-os envx run web -- printenv NAME
      # from-os

      NAME=from-os envx run web --overload=false -- printenv NAME
      # from-os
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `prefix`

  <SchemaMeta type="string" />

  Prepended to every resolved key, uppercased and joined with an underscore, so `app` turns `HOST` into `APP_HOST`.

  - **CLI Flag:** `--prefix`
  - **Environment Variable:** `ENVX_PREFIX`
  - **Default Value:** `""`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        prefix: app

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      port: 8080
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web APP_HOST
      # localhost

      ENVX_PREFIX=svc envx get web SVC_HOST
      # localhost

      envx get web SVC_HOST --prefix svc
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `referencePattern`

  <SchemaMeta type="string" />

  A regular expression that replaces the built-in `{{VAR}}` reference syntax. Capture group 1 is the variable name. The pattern must contain that group. See [Variable substitution](../../concepts/variable-substitution/).

  - **CLI Flag:** `--reference-pattern`
  - **Environment Variable:** `ENVX_REFERENCE_PATTERN`
  - **Default Value:** `\{\{([^}]*)\}\}`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        referencePattern: '\$\{([^}]*)\}'

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      url: http://${HOST}:8080
      literal: http://{{HOST}}:8080
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web URL
      # http://localhost:8080

      envx get web LITERAL
      # http://{{HOST}}:8080

      ENVX_REFERENCE_PATTERN='\{\{([^}]*)\}\}' envx get web LITERAL
      # http://localhost:8080
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `requireOverlays`

  <SchemaMeta type="bool" />

  Require every overlay file in a project's namespace chain to exist. A missing overlay becomes an error instead of being silently skipped.

  - **CLI Flag:** `--require-overlays`
  - **Environment Variable:** `ENVX_REQUIRE_OVERLAYS`
  - **Default Value:** `false`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - staging

      settings:
        requireOverlays: true

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST --env staging
      # ERROR: loading environment file <path>: required overlay file not found

      ENVX_REQUIRE_OVERLAYS=false envx get web HOST --env staging
      # localhost

      envx get web HOST --env staging --require-overlays=false
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

### `suffix`

  <SchemaMeta type="string" />

  Appended to every resolved key, uppercased and joined with an underscore, so `v2` turns `DATABASE_HOST` into `DATABASE_HOST_V2`.

  - **CLI Flag:** `--suffix`
  - **Environment Variable:** `ENVX_SUFFIX`
  - **Default Value:** `""`

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development

      settings:
        suffix: v2

      projects:
        web:
          includes:
            - values
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # values.yaml
      host: localhost
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx get web HOST_V2
      # localhost

      ENVX_SUFFIX=beta envx get web HOST_BETA
      # localhost

      envx get web HOST_BETA --suffix beta
      # localhost
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Secrets

  The optional `secrets` block locates the encrypted secrets store and its keys, and declares the [external providers](../../concepts/secrets-providers/) a workspace may reference. Every key is optional. For how references, groups, and keypairs work, see [Secrets store](../../concepts/secrets-store/).

  ```yaml
  # envx.yaml
  secrets:
    path: secrets.yaml
    keysPath: envx.keys
    cipher: age
    providers:
      op:
        timeout: 30s
  ```

### `path`

  <SchemaMeta type="string" />

  The secrets store file, relative to the manifest. **Default Value:** `secrets.yaml`

### `keysPath`

  <SchemaMeta type="string" />

  The private-key file, relative to the manifest. Keep it out of version control. **Default Value:** `envx.keys`, beside the store

### `cipher`

  <SchemaMeta type={'"age" | "nacl-box"'} />

  The encryption algorithm for the store: `age` or `nacl-box` (NaCl sealed box over Curve25519). It applies to key generation and to every value in the store. A stored value sealed under a different algorithm is not decrypted; [`validate`](../../commands/validate/) reports it as `secret_algorithm_mismatch`. **Default Value:** `age`

### `providers`

  <SchemaMeta type="Providers" />

  Declares which external providers are enabled. A provider that is not declared is disabled, and a value using its scheme passes through unchanged. Each provider takes the keys documented below.

#### `op`

  The 1Password CLI provider.

  | Key | Type | Default | Description |
  | --- | --- | --- | --- |
  | `timeout` | duration | `30s` | Bounds each 1Password CLI call. A positive duration such as `500ms`, `30s` or `2m`. |

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      secrets:
        providers:
          op:
            timeout: 20s
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

#### `bws`

  The Bitwarden Secrets Manager CLI provider.

  | Key | Type | Default | Description |
  | --- | --- | --- | --- |
  | `timeout` | duration | `30s` | Bounds each Bitwarden Secrets Manager CLI call. A positive duration such as `500ms`, `30s` or `2m`. |
  | `project` | map[string]string | | Maps each environment to the project (name or ID) its short references read. May name only declared [`environments`](#environments). |

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - production

      secrets:
        providers:
          bws:
            timeout: 20s
            project:
              development: web-app-dev
              production: web-app-prod
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

#### `passwordstate`

  The Passwordstate provider.

  | Key | Type | Default | Description |
  | --- | --- | --- | --- |
  | `url` | string | | The `https` base URL of the Passwordstate site. |
  | `listId` | map[string]int | | Maps each environment to the list ID its short references read. May name only declared [`environments`](#environments). |
  | `field` | string | `Password` | The field read when a reference names none. |
  | `timeout` | duration | `30s` | Bounds each HTTP request. A positive duration such as `500ms`, `30s` or `2m`. |

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - development
        - production

      secrets:
        providers:
          passwordstate:
            url: https://passwords.example.com
            listId:
              development: 1988
              production: 1989
            field: Password
            timeout: 20s
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>

## Validate

  The optional `validate` block sets the severity of each check that [`validate`](../../commands/validate/) runs. Each key is a check code in camelCase, such as `secretIsNotEncrypted`. Each value is `off`, `warn`, or `error`. A snake_case or SCREAMING_SNAKE_CASE key is rejected.

  Severity is set only here, never on the command line. The matching per-check flag on `validate` is the kebab-case twin of the key, for example `--secret-is-not-encrypted`, and selects which checks run.

  | Key | Default | Reports |
  | --- | --- | --- |
  | `secretIsNotEncrypted` | `error` | A stored value left unencrypted. |
  | `secretAlgorithmMismatch` | `error` | A value stored under a non-configured algorithm. |
  | `secretIsNotReferenced` | `error` | A stored value no environment references. |
  | `publicKeyIsMissing` | `error` | A group with stored secrets but no public key. |
  | `privateKeyIsInvalid` | `error` | A group whose private key is malformed or mismatched. |
  | `privateKeyIsUnavailable` | `warn` | A group with no private key available in this context. |
  | `secretReferenceNotFound` | `error` | A reference to a value absent from the store. |
  | `invalidSecretReference` | `error` | A malformed secret reference. |
  | `secretReferenceIsUnresolved` | `error` | A reference that passed every store check yet failed to decrypt. |
  | `circularVariableReference` | `error` | A variable substitution cycle. |
  | `unresolvedVariableReference` | `error` | A substitution of an undefined variable. |
  | `propertyNotDeclaredInBase` | `off` | An overlay key its namespace base file never declares. |
  | `invalidExternalReference` | `error` | A malformed reference for an enabled external provider. |
  | `externalProviderNotEnabled` | `warn` | A value using the scheme of an undeclared external provider. |
  | `externalProviderUnavailable` | `error` | A declared external provider that cannot be used. |
  | `externalReferenceUnresolved` | `error` | An external reference the provider could not resolve. |

  <ExampleAccordion>
  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      validate:
        privateKeyIsUnavailable: error
        propertyNotDeclaredInBase: warn
        secretIsNotReferenced: off
      ```
    </Fragment>
  </ExampleBox>
  </ExampleAccordion>
