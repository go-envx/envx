envx provides a built-in approach for storing encrypted values in a `secrets.yaml` file that is safe to commit. The `<namespace>.yaml` files can refer to secrets with a `secret://` reference that envx decrypts when it resolves the environment.

:::tip[Recommendations]
- Use the [`envx secrets`](../../commands/secrets/) and [`envx keypair`](../../commands/keypair/) commands to write and update `secrets.yaml` and `envx.local.keys`. They generate keys, encrypt values, and keep both files consistent, which is safer than editing them by hand.
- Groups do not have to match the environments in `envx.yaml`, but in most cases they should. One group per environment (for example `development` and `production`) keeps each environment's secrets under its own keypair.
:::

## Key concepts

| Concept | Role |
| --- | --- |
| `secret://<group>/<key>` | A reference to a stored value. Place it anywhere a value is allowed in a `<namespace>.yaml` file, and envx decrypts it when it resolves the environment. |
| `secrets.yaml` | The secrets store: holds each group's public key and its encrypted values. It is safe to commit. |
| `envx.local.keys` | Holds each group's private key. It is git-ignored and must never be committed. |

:::danger[Never commit `envx.local.keys`]
`envx.local.keys` holds private keys that decrypt every value in `secrets.yaml`. Anyone who obtains it can read your secrets, and removing it from git history does not undo the exposure. Keep it in `.gitignore`, and if it is ever committed or shared, rotate the affected groups with [`envx keypair rotate`](../../commands/keypair/).
:::

A few terms are worth naming up front:

- A **group** is a case insensitive name that shares one keypair. It cannot contain whitespace, `/`, or `=`, and it is normalized to lowercase.
- A **key** names a value within a group. It is case-sensitive and cannot contain `/` or a line break.
- A **keypair** is the asymmetric pair for a group. The **public key** lives in `secrets.yaml` and encrypts, so anyone with the store can add values. The **private key** lives in `envx.local.keys` by default and decrypts the secret values stored in `secrets.yaml`. See [Private-key lookup](#private-key-lookup) for other sources.

Other URL-like values pass through unchanged, and `\secret://group/key` is an escaped literal, not a reference. A malformed reference is an error. To change the store location, key file, or cipher, see the [`secrets` block](../../configuration/schema/#secrets) of `envx.yaml`.

## Example

The files below show how a reference in a namespace file points at a value in the store, and where the private key lives.

  <ExampleBox>
    <Fragment slot="manifest">
      ```yaml
      # envx.yaml
      environments:
        - prod

      projects:
        api:
          includes:
            - env/database
      ```

      ```yaml
      # env/database.yaml
      database:
        host: localhost
        password: secret://prod/db_password
      ```
    </Fragment>
    <Fragment slot="files">
      ```yaml
      # secrets.yaml
      public-keys:
        prod: age1...
      secrets:
        prod:
          db_password: encrypted-age:AwQF...
      ```

      ```ini title="envx.local.keys"
      PROD=AGE-SECRET-KEY-1...
      ```
    </Fragment>
    <Fragment slot="commands">
      ```sh
      envx keypair generate prod
      envx secrets set prod db_password
      envx get api DATABASE_PASSWORD --reveal
      ```
    </Fragment>
  </ExampleBox>

Here `secret://prod/db_password` resolves to the `db_password` value in the `prod` group of `secrets.yaml`. To decrypt it, envx reads the group's private key from `envx.local.keys`. The commands above create the keypair and the encrypted value, then print the decrypted result.

See [`keypair`](../../commands/keypair/) and [`secrets`](../../commands/secrets/) for every command.

## Private-key lookup

When envx needs a group's private key, it uses the first source that has one:

1. `ENVX_PRIVATE_KEY_<GROUP>`, with the group name in uppercase, holding that group's key. For a single group, set the group's variable:

   ```sh
   export ENVX_PRIVATE_KEY_PROD="AGE-SECRET-KEY-1..."
   envx run api -- node server.js
   ```

2. `ENVX_PRIVATE_KEY`, holding a bundle of `GROUP=key` lines, one per group. For several groups, set the bundle with one `GROUP=key` line per group:

   ```sh
   export ENVX_PRIVATE_KEY="
     PROD_DB=AGE-SECRET-KEY-1Q7X...
     PROD_REDIS=AGE-SECRET-KEY-1M4K...
   "
   envx run api -- node server.js
   ```

3. The `envx.local.keys` file, or the path set by `secrets.keysPath`.

:::tip[Recommendations for CI/CD]
In CI and containers, supply the key through the environment with `ENVX_PRIVATE_KEY_<GROUP>` or `ENVX_PRIVATE_KEY`.
:::

## Masking and `--reveal`

<MaskingAndReveal />

:::danger[Never commit unencrypted values]
Files written by `envx secrets decrypt` or `envx emit --output` hold unencrypted values and must not be committed. Re-encrypt the store with `envx secrets encrypt` before committing it.
:::
