# Validate, Pack, Emit, and External Secret Providers

This plan covers the next envx increment: a single `validate` command that runs every workspace check, a `pack` command that packages the workspace for deployment, an `emit` command that renders a resolved environment to a delivery target, and external secret providers so a workspace is not forced onto envx's own crypto. It supersedes the variable-substitution plan (now shipped — see **Shipped**) and folds that plan's leftover documentation task into a single docs pass (Task 5, the last task before the release; providers follow as post-release work). Each task is one independently reviewable pull request.

**One check command, not three.** An earlier draft split checks across three commands (`audit`, `lint`, `validate`). They are collapsed into one `validate` command because the earlier split's real benefit — running a fast, offline subset in a pre-commit hook — is better served by *selecting checks* within one command than by three separate commands with overlapping logic. Neither `audit` nor `lint` was ever built, so the merge costs no compatibility.

`validate` runs two groups of checks, split by **which files a check reads** — which is also the **cost boundary**, so a hook can select only the cheap group:

| Group | Reads | Cost | Checks |
| --- | --- | --- | --- |
| **store** | `secrets.yaml` (+ keys file) | offline, instant | unencrypted secret · algorithm mismatch · unused secret · missing public key · invalid private key · missing private key |
| **resolution** | namespace files (merged per project × environment) | heavier; later network once providers land | secret reference not found · invalid secret reference · unresolved secret reference · circular variable reference · unresolved variable reference · property not declared in base |

Every check has a single owner, so no problem is reported twice: encryption and key *health* belong to the store group; the resolution group reports only reference/variable *resolution* structure. Each check's severity (`off` / `warn` / `error`) is configurable through a root-level `validate:` block in `envx.yaml` (config-file only, never a CLI flag). Defaults are `error` for every check except a missing private key, which defaults to `warn` because it is normal on a developer laptop, and the base-declaration check, which defaults to `off` because it is an opt-in best practice. Per-check boolean flags select a subset for a hook and skip the cost of the rest (`envx validate --secret-is-not-encrypted --public-key-is-missing`); `--strict` promotes every remaining `warn` to `error` for a full-CI gate.

## Shipped (context, not work)

The substitution feature is delivered on `main`/this branch: reveal-gated `{{VAR}}` substitution over the composed effective environment (a single reference syntax that resolves against the merged files and OS environment, ordered by `overload`), the effective-environment/overload centralization in [envmerge](app/internal/envmerge/), `run --ignore-errors`, and a configurable reference pattern (`reference_pattern`). The diagnostic engine is also in place: [`envmerge.Diagnose`-style resolution](app/internal/envmerge/resolution.go), the `ValueDiagnoser` seam, and the redesigned `explain` that reports per-key `TYPE`/`LITERAL`/`SOURCE`/`STATUS` and exits `0`. `validate` and `emit` build directly on that diagnostic engine.

The first slice of `validate` is also already built on this branch (Task 1): the workspace-wide engine, the reference and store findings, the graded `Report`, `--strict`, `config.ResolveWorkspaceProjects`, and the table/JSON renderer. Before Task 1 is committed it also absorbs the code centralization/rename, grading-by-code, and the `validate:` severity config (see Task 1). The rest of the unified `validate` — the per-check selection flags, the offline cost gating, and the new checks (missing public key, algorithm-mismatch-as-store, property-not-declared-in-base) — lands in Task 2 on top of it.

The substitution plan's leftover `disable_substitution` setting is **not** carried forward: the `\{{VAR}}` escape covers any single literal value, and a configurable `reference_pattern` that never matches can disable the syntax workspace-wide, so a dedicated global setting is redundant. It can be revisited if a concrete need appears.

## What we're building

1. **`validate`** — the one workspace check command. It runs the **store** group (offline checks over `secrets.yaml`: unencrypted secret, algorithm mismatch, unused secret, missing public key, invalid private key, missing private key) and the **resolution** group (over every project × environment merge: secret reference not found, invalid secret reference, unresolved secret reference, circular variable reference, unresolved variable reference, property not declared in base). Every finding is collected and the scan never aborts mid-run. Each check's severity is set in a root-level `validate:` block in `envx.yaml` (`off`/`warn`/`error`, config-file only); defaults are `error` except a missing private key (`warn`) and the opt-in base-declaration check (`off`). Per-check boolean flags run a chosen subset and skip the cost of the rest, so a pre-commit hook can run only the offline store checks; `--strict` promotes remaining warnings to errors for CI. It can hit the network once providers land (resolution group only). `explain` stays single-environment and always exits `0`; `validate` is all-environment and can fail.

2. **`pack`** (item 1a) — copy an *environment-scoped subset* of the workspace files into an isolated output directory: the manifest, each project's include files (base `<name>.yaml` plus only the selected environments' `<name>.<env>.yaml` overlays), and a *filtered* `secrets.yaml`, **excluding** the private keys. The bundle uses a **per-project layout**: each project gets its own `<project>/` directory holding every namespace file it includes, and the manifest's `includes` are rewritten to `<project>/<name>` to match. A file two projects both include is copied into each project's directory; the `secrets.yaml` store stays a single file at the bundle root, filtered to the *union* of the selected projects' references and stripped of the `public_keys` block, because a bundle only runs, never encrypts; a workspace that references no secret carries no store at all. Because the store lives at the root, a single project directory is not runnable on its own — for per-project secret isolation, run `pack` once per project into a separate output. `-e` is repeatable and selects one or more environments (default: all declared), so a single copied directory can serve several environments — `envx pack -e staging -e production --out ./dist`. An existing, non-empty `--out` directory is refused unless `--force` is passed. Secrets stay encrypted; nothing is decrypted. The directory is copied into a Docker image and run with the ordinary pipeline — `envx run api --env production --config /app/envx.yaml -- <cmd>` — decrypting with `ENVX_PRIVATE_KEY` from the environment. This reuses the existing run path verbatim: no new file format, no new run source, and one image can run any of the copied environments by passing `--env` at container start.

3. **`emit`** (item 1b, and optional foreign export) — fully resolve and decrypt a *single* environment at emit time and render it to a selected format. The `k8s` target splits secret-derived values into a `Secret` and the rest into a `ConfigMap` so a GitHub Action can `kubectl apply` them directly (keys live in GitHub as CI secrets; the Action resolves everything); `k8s-bundle` packs a slice into a single JSON data key for volume-mounting as one file; `--only secrets|config` restricts either target to one slice. Plain `dotenv`/`json` targets emit plaintext for non-envx consumers.

4. **External secret providers** — new reference *schemes* (`bitwarden://…`, `passwordstate://…`) that resolve at reveal time through a provider interface, sitting alongside the existing `secret://`. envx's local crypto stays available; providers are opt-in per reference. This lets teams keep their existing secret manager instead of migrating into the envx store.

5. **Base-declaration best practice** — requiring every key in an environment overlay to also be declared in its namespace's base file, so the base becomes the single catalog of every key and an overlay-key typo is caught instead of silently creating a new key. It is purely the resolution group's `property-not-declared-in-base` check, reported at its configured severity (default `off` — an opt-in best practice a workspace enables by setting it `warn`/`error` in the `validate:` block, so it never surprises an existing workspace on upgrade). It is a `validate`-only concern: `run`/`emit`/`pack` do not enforce it (see **Out of scope** — no pipeline enforcement of advisory checks), so a team that wants it as a hard gate runs `validate` in CI.

6. **Docs** — one pass bringing the site docs current with everything since they were last updated (substitution, overload, `--ignore-errors`, configurable patterns) plus `validate` (the check groups, the per-check severity config, the selection flags, the pre-commit hook), `pack`, `emit`, the base-declaration policy, and providers.

## Design decisions (locked)

### `pack` (deployable source bundle)

- **Copy the workspace files, scoped — don't render a single file.** Rather than rendering the environment into a custom single file with inline-encrypted tokens, `pack` copies the workspace files as-is (scoped to the selected environments) into an output directory, and the container runs the ordinary pipeline against it. This deliberately trades "one flat file" for "no new file format and no new runtime path": the artifact runs through the exact same `envx run` that dev uses, so encrypted secrets decrypt at runtime unchanged and there is nothing new to keep in sync. (An earlier draft used a group-tagged inline-ciphertext token with a new `run --from` source; it was dropped as strictly more machinery for the same outcome.)
- **Per-project directory layout.** The bundle groups files by project: each project gets its own `<project>/` directory holding every namespace file it includes, and the manifest's `includes` are rewritten to `<project>/<name>` to match. A file two projects both include is copied into each project's directory, so a project directory is self-contained for its namespace files. The files' *contents* are copied byte-for-byte and merged by the exact same `run` path — packing rehomes files, it does not re-derive values (a per-project consolidation that pre-merges the include chain was considered and rejected: envx merges per-namespace in declaration order, so collapsing chains would change precedence and force a partial evaluator). (An earlier draft flattened every namespace into the output root under its include's final segment, disambiguating basename collisions with numeric suffixes; it was replaced by the per-project layout — shipped in #114 — so a namespace's project of origin is legible and cross-project basename collisions are structurally avoided.)
- **Multi-environment by design.** `-e` is repeatable and selects one or more environments (default: all declared). The copied directory keeps every selected environment's overlays, so **one image serves several environments** — the container picks one at start with `envx run api --env production --config <dir>/envx.yaml`. This is a capability a per-env flat file cannot offer and a direct reason to keep the real workspace.
- **Environment-scoped, filtered, and key-free.** The bundle includes the manifest, each project's include files (base + only the selected environments' overlays), and a filtered `secrets.yaml`; it **excludes** the private keys (supplied at runtime via `ENVX_PRIVATE_KEY`), unselected environments' overlays, and every `public_keys` entry (a bundle only runs, never encrypts). The `secrets.yaml` store stays a single file at the bundle root and keeps **only the values the selected environments reference** — pack scans the bundled namespace files' leaf values for `secret://group/key` references (matching resolution exactly, no decryption) and retains just those group/key entries, filtered to the *union* of the selected projects' references; a workspace that references no secret carries no store file at all. Because the store lives at the root, a single project directory is not runnable on its own — for per-project secret isolation, run `pack` once per project into a separate output. Scope defaults to the whole workspace; `--project`/`-p` narrows which projects' includes are copied.
- **Paths are rewritten for the per-project layout.** The copied manifest's `includes` are rewritten to `<project>/<name>` and its `secrets` path to the root store (via YAML node editing, preserving comments and formatting). The `keys_path` is left as declared — harmless, since the key file is never copied and `ENVX_PRIVATE_KEY` wins at runtime. This is the one nontrivial part of `pack`.
- **A non-empty `--out` is refused unless `--force`.** So a bundle never merges into stale files; `--force` clears the directory and packs fresh.
- **Runtime reuses `run --config`, no new run source.** No `--from` flag or flat-file parser is added.
- **Providers need no special-casing.** A `bitwarden://` reference resolves at runtime through the normal provider path (given provider access in the container), because the bundle is a real workspace, not a flattened snapshot. (Note: pack's referenced-secret filtering only trims the local `secret://` store; provider references are copied through in the namespace files like any other value.)

### `emit` (materialized render)

- **Single environment, fully resolved, never partial.** `emit` resolves and decrypts one environment at emit time; a missing key aborts before any output. Multi-environment fan-out is `pack`'s job, not `emit`'s.
- **Kubernetes splits by kind.** The `k8s` target renders both a v1 `Secret` (base64 `data`, the secret-derived/provider values) and a v1 `ConfigMap` (the rest), each value its own data key (consume with `envFrom`); `--only secrets|config` restricts output to one slice. `k8s-bundle` instead packs the selected slice into a single JSON data key so the resource can be volume-mounted as one file (`--key` names the data key / mounted filename, its `.json`/`.env` extension picking the body format). Resource names default to `<project>-config` / `<project>-secrets` (a merged bundle `<project>-config-secrets`); `--name` overrides. `dotenv`/`json` targets emit plaintext for non-envx consumers.

### External providers

- **Providers are reference resolvers, not a store replacement.** A provider satisfies a small interface that, given a parsed reference and a reveal policy, returns the value (or a diagnostic in dry-run). The existing [secrets.Resolver](app/internal/secrets/resolver.go) becomes one provider among several behind a scheme-dispatching resolver; `secret://` keeps its exact current behavior.
- **Scheme dispatch composes with substitution.** Reference resolution already runs as a [ValueResolver](app/internal/envmerge/params.go) stage before `{{ }}` substitution, so a provider value can be referenced by `{{VAR}}` like any other. Providers plug in at the config composition layer ([config.resolverFactory](app/internal/config/config.go)), not inside envmerge.
- **Provider config is workspace-level.** Provider connection settings (endpoint, auth-token env var, org/vault identifiers) live under a `secrets.providers` block in `envx.yaml`, keyed by scheme. Credentials themselves are never stored in the manifest — they name an env var (e.g. `BWS_ACCESS_TOKEN`) read at reveal time, mirroring how `ENVX_PRIVATE_KEY` is sourced.
- **Masked mode never contacts a provider.** Masking echoes the canonical reference (`bitwarden://item/field`) without network I/O, exactly as `secret://` masking does today. Only reveal (and `validate` dry-run status, which reports reachability without exposing the value) may contact a provider.
- **Diagnostics extend, they don't fork.** Each provider maps its failure modes onto the existing `Severity`/`Code` model ([resolution.go](app/internal/envmerge/resolution.go)): unreachable/unauthorized → warning or error with a stable code, not-found → error. No plaintext or credential material ever appears in a code or message.

### `validate` (the one check command)

- **Checks are grouped by the files they read, which is also the cost boundary.** The **store** group reads only `secrets.yaml` (+ the keys file) and is offline and instant; the **resolution** group merges each project × environment (and later reaches the network for providers). A hook selects the store group and pays nothing for resolution. This is what lets one command replace the earlier `audit`/`lint`/`validate` split.
- **Every check has exactly one owner — no finding is reported twice.** Value *health* — encrypted, correct algorithm, keypair valid, keypair available — is owned entirely by the store group (all facts about `secrets.yaml`, true regardless of any reference). The resolution group reports only reference/variable *resolution* structure: a reference that points nowhere (`SECRET_REFERENCE_NOT_FOUND`), is malformed (`INVALID_SECRET_REFERENCE`), or a value that passed every store check yet still failed to decrypt (`SECRET_REFERENCE_IS_UNRESOLVED` — corrupt ciphertext), plus the variable and base-declaration checks. A missing key, invalid key, unencrypted value, or algorithm mismatch is reported once, by the store group; the resolution group never re-reports it. `explain` keeps its full per-reference diagnosis (it is the single-environment view and users want the per-key cause there); `validate` grades each finding **by its code** and lets the store group own the cause, so the two never duplicate.
- **Canonical status codes live in one leaf package** shared by `validate` and the `secrets`/`envmerge` diagnosers, replacing today's three duplicated definitions. Each code carries its default severity there. The set (default `error` unless noted):

  | Check | Group | Code | Default |
  | --- | --- | --- | --- |
  | unencrypted secret | store | `SECRET_IS_NOT_ENCRYPTED` | error |
  | algorithm mismatch | store | `SECRET_ALGORITHM_MISMATCH` | error |
  | unused secret | store | `SECRET_IS_NOT_REFERENCED` | error |
  | missing public key | store | `PUBLIC_KEY_IS_MISSING` | error |
  | invalid private key | store | `PRIVATE_KEY_IS_INVALID` | error |
  | missing private key | store | `PRIVATE_KEY_IS_UNAVAILABLE` | **warn** |
  | secret reference not found | resolution | `SECRET_REFERENCE_NOT_FOUND` | error |
  | invalid secret reference | resolution | `INVALID_SECRET_REFERENCE` | error |
  | unresolved secret reference | resolution | `SECRET_REFERENCE_IS_UNRESOLVED` | error |
  | circular variable reference | resolution | `CIRCULAR_VARIABLE_REFERENCE` | error |
  | unresolved variable reference | resolution | `UNRESOLVED_VARIABLE_REFERENCE` | error |
  | property not declared in base | resolution | `PROPERTY_NOT_DECLARED_IN_BASE` | **off** |

  (`missing private key` keeps the `UNAVAILABLE` wording rather than `MISSING` because on a laptop the key is not absent from the workspace, it is merely not available in this context — which is exactly why it defaults to `warn`.) These codes also surface in `explain`, so renaming them updates `explain`'s output and tests; acceptable pre-1.0.
- **Severity is assigned by code, from config, not by the diagnoser.** `validate` grades every finding by looking its code up in the resolved severity map (config override, else the code's default). This replaces Task 1's hardcoded per-finding severities and the copying of the envmerge resolution severity, so one code has one severity everywhere. A code mapped to `off` is dropped entirely.
- **Severity is configured in `envx.yaml` only, never on the CLI.** A root-level `validate:` block maps each check (by its lowercased code, e.g. `secret_is_not_referenced`) to `off` / `warn` / `error`. This is deliberately *not* a flag: severity policy is a property of the workspace, committed and identical everywhere, so it cannot drift between a laptop and CI.
- **`--strict` is the CI escalation the shared config can't express.** Because `envx.yaml` is identical on a laptop and in CI, `--strict` (a CLI flag) is what a full-CI gate uses to promote every remaining `warn` to `error` — chiefly the missing-private-key warning, tolerated locally but a failure where every key is expected. Everything is still reported; the scan never aborts mid-run. `explain` is the always-exit-`0` diagnostic; `validate` is the enforcement one.
- **Per-check boolean flags select a subset and skip the rest's cost.** A hook runs, e.g., `envx validate --secret-is-not-encrypted --public-key-is-missing`; only the named checks run, and if none of them need a merge, no merge happens. Passing any check flag switches from "run all" to "run only these." The flag *selects* a check to run; its severity still comes from config (plus `--strict`), so the all-`error` default makes selection-for-a-hook behave as "fail on this." (Flag naming was resolved: each per-check flag is named identically to its severity key in the `validate:` block — `--secret-is-not-encrypted` selects the check configured by `validate.secret_is_not_encrypted` — so one name means the same check in the config and on the command line.)
- **Never materializes plaintext.** Every check computes status only, reusing the reveal gate's dry-run path.

### The base-declaration policy

- **It is a resolution-group check, reported at its configured severity.** `PROPERTY_NOT_DECLARED_IN_BASE` fires when an environment overlay declares a key its namespace base file does not. It **defaults to `off`**: the convention is a best practice, not every workspace follows it, and defaulting it on would fail existing workspaces the moment they upgrade. A workspace opts in by setting it `warn`/`error` in the `validate:` block. There is no separate `lint` command.
- **It is a `validate`-only concern; the pipeline does not enforce it.** `run`/`emit`/`pack` follow "resolve what is asked; fail closed only when the requested resolution itself is unsafe" — and an overlay-only key resolves perfectly well, so they proceed. Anything that *would* make the current resolution wrong or unsafe (a dangling reference, a plaintext store value, a missing/invalid key or algorithm mismatch on a *referenced* secret) already fails the pipeline at resolution time; base-declaration is orthogonal to that, a quality convention with no bearing on whether this environment resolves. A team that wants it enforced as a hard gate runs `validate` in CI, which is the right place for it — it fails fast, before the deploy job, with every finding at once. (An earlier draft added a `require_base_declaration` bool making the pipeline fail closed; it was dropped — see **Out of scope**.)
- **Provenance is already available.** envmerge records each key's winning source and every shadowed source ([Origin](app/internal/envmerge/materialize.go)); a base file (`<name>.yaml`) is distinguished from an overlay (`<name>.<env>.yaml`) by filename, so the check reads existing merge state without a new pass.

## Architecture

The new packages follow the existing thin-action / typed-engine split. Existing symbols keep their shape; additions land only in the task that needs them. The relevant contracts (`Kind`, `Severity`, `Resolution`, `ValueDiagnoser`, `Diagnose`, `Literal`, `Resolution` accessors, and the secret-reference status map) are already specified and partially implemented; this plan reuses them and adds:

- **`internal/pack`** (built in Task 3) — resolves the workspace layout, computes the environment-scoped file set across the selected projects, places each project's namespace files under a `<project>/` directory, rewrites the manifest's includes (to `<project>/<name>`) and secrets path via YAML node editing (`manifest.go`), scans the bundled namespace files for referenced `secret://` values (`references.go`), and writes the bundle — copying namespace files, the rewritten manifest, and a single root filtered, public-key-free secrets store. Excludes the private keys. No decryption. The store filtering lives in `secrets.WriteFilteredStore` (`internal/secrets/pack.go`) over new `store` document methods `RetainSecrets`/`RemovePublicKeys`/`SaveTo`; `config.ResolveWorkspaceLayout` supplies the file-level workspace view without building an envmerge Manager.
- **`internal/emit`** (new) — a materialize renderer with `Target` (`dotenv`, `json`, `k8s`, `k8s-bundle`) and a `Render` entry point over the existing reveal build path, plus an `--only secrets|config` slice selector. No new secrets resolver mode and no `run --from` are needed.
- **`internal/provider`** (new) — the provider interface, a scheme registry, and the `bitwarden` and `passwordstate` implementations. `config` composes the registry into the resolver factory; envmerge is untouched (it already consumes the `ValueResolver` seam).
- **`internal/validate`** (built in Task 1, extended in Task 2) — the single check engine. Task 1 shipped `Finding`/`FindingKind` (`reference`, `orphan`, `plaintext`, `keypair`), `Report{Findings, Errors, Warnings, Failed}`, `Params{Strict}`, `Validate(Workspace, Params)`, and the `config.ResolveWorkspaceProjects` helper that iterates every project × environment. Task 2 turns it into a **check registry**: each check declares its group (`store`/`resolution`), its cost (so selecting only store checks skips the merge), its canonical code, and its default severity; `Params` gains the per-check severity map (from config) and the selected-check set (from flags). The base-declaration check and the missing-public-key check are added here.
- **`internal/status`** (new leaf) — the canonical status codes and default severities shared by `validate`, `secrets`, and `envmerge`, so the codes are defined once instead of duplicated across three packages. `secrets.Diagnose` and the envmerge substitution diagnoser emit these codes; `validate` keys severity config off them. (Exact package name TBD; it must be importable by both `secrets` and `validate` without a cycle.)
- **`internal/schema` / `internal/config` / actions** — new `FlagSpec`s and flag wiring for `pack` (repeatable `-e`/env, `--out`, `--project`), `emit` (target, name, output path), `validate` (`--strict` plus the per-check selection flags), the root-level `validate:` severity block parsed from `envx.yaml` (config-file only, no flag/env binding), and the `secrets.providers` manifest block. Actions stay thin Cobra adapters that parse flags, call the engine, and render.

## Out of scope

- **A single-file artifact with inline-encrypted secrets.** `pack` reorganizes the *directory layout* (one `<project>/` directory per project) but keeps one file per namespace and a separate encrypted store; it does not render the environment into a single self-describing file with inline ciphertext. Revisit only if a single portable envx-decodable file is specifically needed.
- **Rewriting a copied manifest beyond includes/secrets-path rewriting** (e.g. pruning the `environments:` list, or pruning an unselected project's includes when `--project` narrows scope — those stay in the copied manifest, harmless since only the run project's includes are read). `pack` rewrites the `includes` and `secrets` path for the per-project layout and otherwise leaves the manifest as-is.
- **Pipeline enforcement of advisory checks (a `require_validation` / `require_base_declaration` gate).** `run`/`emit`/`pack` do not run `validate` before executing and gain no setting to make them fail closed on an advisory finding. They already fail closed on anything that makes the *requested* resolution unsafe — a dangling reference, a plaintext store value, a missing/invalid key or algorithm mismatch on a referenced secret all abort at resolution time — so a pre-run gate would add only the ability to block on *quality* problems orthogonal to the current run (base-declaration, unused secret, missing public key). That belongs in CI: run `validate` there. An earlier draft added a `require_base_declaration` bool (and a broader `require_validation` was considered); both were dropped to keep one model — `run`/`emit`/`pack` resolve what is asked, `validate` is the quality gate.
- **Provider *write* operations.** Providers resolve (read) references; creating/rotating secrets in Bitwarden or Passwordstate is not in this plan.
- **A `validate --install-hook` convenience.** The pre-commit hook (selecting the offline store checks) is documented and installed manually; a built-in installer is deferred.
- **Separate `audit` and `lint` commands.** Folded into `validate` as the store check group and the base-declaration check; revisit only if a genuinely different command surface is needed.
- **Additional static checks** (duplicate keys, naming conventions, unused includes). The check registry is the seam for them, but they are not in this plan.
- **Command substitution** (running a shell command); the reserved kind stays unimplemented.
- **Windows case-insensitive environment-variable matching** (unchanged from the substitution plan's constraints).
